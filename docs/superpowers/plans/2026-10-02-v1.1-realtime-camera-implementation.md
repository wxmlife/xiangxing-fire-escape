# 巷行 V1.1 实时摄像头与动态改路 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 在不破坏照片上传流程的前提下，为固定俯拍的技拓 USB 摄像头加入取流、基准配准、动态火源/障碍识别、保守防抖、版本化动态改路与七人实时仿真。

**Architecture:** 摄像头层只负责标准 `getUserMedia`、抽帧和状态；每帧先配准到已确认基准，再通过与照片相同的 `SceneRevision 1.1` 感知管线生成候选修订。独立的时序门禁先选出已通过安全防抖的精确语义/掩膜补丁，修订流再从当前修订仅物化这些 accepted patches，绝不把同帧尚在 pending/rejected 的“通道重开”夹带进新版。最新版门禁阻止旧 Worker 结果覆盖新地图；动态规划器和仿真控制器只消费不可变修订，不引用摄像头或颜色阈值。

**Tech Stack:** 原生 JavaScript ES modules、MediaDevices/getUserMedia、HTMLVideoElement/Canvas/OffscreenCanvas、Web Worker、Page Visibility API、Node.js `node:test`、GitHub Pages（无构建步骤、无 `SharedArrayBuffer` 依赖）。

**Spec:** `docs/superpowers/specs/2026-10-02-v1.1-realtime-recognition-routing-design.md`

## Global Constraints

- 产品只用于受控教学沙盘与算法演示；任何实时状态都不得表述为真实火场安全认证。
- 摄像头固定在沙盘正上方并完整覆盖沙盘；机位超出配准容差后必须暂停实时结论并要求重校准。
- 只在用户点击“连接实时摄像头”后调用 `getUserMedia`；不支持 RTSP，也不绕过操作系统驱动。
- 始终保留同等明显的“拍照或上传图片”入口；摄像头不可用、权限拒绝或断流不得阻塞照片模式。
- 预览目标为 15–30 fps；分析档固定为 `640×480 @ 2 fps` 与降级档 `480×360 @ 1 fps`。
- 2 fps 档高置信危险到封路 p95 ≤ 1.5 s、中置信 ≤ 2 s；1 fps 档对应 ≤ 2 s 与 ≤ 3 s，界面显示实际档位和上限。
- 摄像头断流、页面进入后台或最后有效帧超过 2,000 ms 时进入 `STALE`，停止宣称路线实时安全并自动暂停仿真。
- 高置信新火源/新障碍命中活动路线时单帧立即封闭；中置信新阻断须持续至少 500 ms 且连续两次采样；移除在 2 fps 档稳定 2,000 ms、1 fps 档稳定 3,000 ms 后才开放。
- 其他变化合并 250 ms；新高安全桶立即换路，同安全桶且堵塞改善超过误差时换路，二者同级时仅 ETA 改善至少 10% 且稳定 1,000 ms 才换路。
- 规划和感知默认在普通 Worker 中运行；无 Worker 或 OffscreenCanvas 时降为 1 fps，不能依赖跨域隔离或 `SharedArrayBuffer`。
- 每个感知、规划与仿真结果必须绑定精确 `revisionId`；旧修订的晚到结果不得覆盖新修订。
- 实时内存环形缓冲最多 120 个修订；仅基准确认、人工修改、触发改路、用户保存或正式运行引用的修订持久化。
- 未经事后复核的实时运行只能进入历史，不进入正式排行榜。
- 摄像头只观察沙盘变化，不追踪真人位置；七位逃生者始终是虚拟仿真对象。
- 复用核心计划已经固定的 `dist/core/*` 与 `dist/workers/*` 接口，不新增第二套 Scene、感知、道路、规划、仿真或存储模型。

## Review Focus

- 用户拒绝权限或浏览器无视频 API：只请求一次并给出照片入口，不循环弹权限（Task 2 测试）。
- 轨道存在但视频停止产出、页面后台或 USB 被拔出：2 秒内进入 `STALE`，冻结仿真且旧路线不再标“实时安全”（Task 9 测试）。
- 较旧的感知/规划 Worker 在较新修订后返回：结果必须被丢弃，reservation 永久消费且不能回滚地图或路线（Task 7、8 测试）。
- 相机位移、模糊或遮挡使配准失真：进入“需要重新校准”，不能把整幅错位误报成移动障碍（Task 4 测试）。
- 动态重规划输入缺人、时间倒退或路线从原绿门重启：请求必须拒绝或从七人权威 `SimulationSnapshot.evacuees[].currentPosition`/`simTimeMs` 续跑，绝不读 `currentGridCell`、瞬移或清零（Task 8、9 测试）。
- 同一帧既有立即接受的新火源，又有尚未达重开延时的障碍移除：新修订只能加入火源，原障碍和封路必须保留（Task 5–7 测试）。
- 摄像头静帧经人工编辑/复核后保存：原子写入必须是当前 reviewed child revision 加最初静帧的 `imageRecord`，不得回存未修正 candidate（Task 10 测试）。

## Prerequisite Core Interfaces

开始本计划前，核心实现计划必须已提供下列接口；本计划只调用，不复制实现：

- `dist/core/contracts.mjs`: `createRevisionReservation({ sceneId, parentRevisionId, sequenceNo, source, capturedAt }, { idFactory, now } = {})`、`validateSceneRevision(revision)`；reservation 是感知前创建的冻结对象，字段为 `schemaVersion:'1.1'`、scene/revision/parent ID、sequenceNo、source、capturedAt。
- `dist/core/calibration.mjs`: `warpToBoard(imageData, calibration)`。
- `dist/core/photo-input.mjs`: `DecodedPhoto = { orientedImageData, source: { fileName, detectedMime, byteLength, width, height }, release() }`；`release()` 必须可重复调用。一旦 `DecodedPhoto` 交给 `createCandidateRevisionFromImage(...)`，核心 pipeline 就在自身 `try/finally` 中独占释放责任，并在成功、失败、abort 各路径精确调用一次；调用方不得二次释放，只在交接 pipeline 之前失败或取消时调用一次。
- `dist/core/scene-pipeline.mjs`: `createCandidateRevisionFromImage({ reservation, requestId, decodedPhoto, detectedCorners, manualCorners, adapter, thresholdProfile, retainNormalizedFullOriginal = false, originalConsentAt = null, signal, onProgress }): Promise<CandidateRevisionBundle>`。
- `CandidateRevisionBundle = { revision, imageRecord }`，`revision.revisionId === reservation.revisionId`；`imageRecord` 精确含 `{ hash, width, height, mime, boardBlob, thumbnailBlob, normalizedFullOriginalBlob, originalConsentAt }`。
- `dist/core/perception-adapter.mjs`: `PerceptionAdapter.recognize({ requestId, revisionId, imageData, calibration, thresholdProfile, signal, onProgress })`；`createWorkerPerceptionAdapter(client, { recognizerId = 'heuristic-browser', modelVersion = 'heuristic-1.1.0' } = {})`。
- `dist/core/road-network.mjs`: `extractRoadNetwork({ masks, obstacles, calibration, profile })`、`measureRoadBlockage({ roads, baselineMasks, currentMasks, uncertainty, profile })`。
- `dist/core/worker-client.mjs`: perception client 提供 `recognize(request, { signal, onProgress } = {})`；planning client 提供 `plan(request, { signal, onUpdate } = {})`；二者均提供 `cancel(requestId)`、`dispose()`。`onUpdate` 接收同 requestId/revisionId 的 `PLAN_UPDATE`，最终 Promise 只由 `PLAN_RESULT` 结算。
- `createPerceptionWorkerClient(worker, { timeoutMs = 15_000, setTimer, clearTimer })` 超时会取消请求并以 `code:'WORKER_TIMEOUT'` 拒绝；worker-backed adapter 必须是 scene pipeline 的 adapter，UI/实时层不能旁路 pipeline 自行拼 revision。
- 感知 request 精确为 `{ requestId, revisionId, imageData, calibration, thresholdProfile }`；规划消息精确为 `PLAN_REVISION { type, requestId, revisionId, revision, profile, plannerVersion, maximumSearchNodes, mode, startState }`，且 Worker 校验顶层 `revisionId === revision.revisionId`。
- `dist/core/worker-client.mjs`: `createLatestRevisionGate()` 返回 `{ begin(revisionId), isCurrent(token), commit(token, fn), cancelCurrent() }`。
- `dist/core/lexicographic-routing.mjs`: `generateRouteCandidates({ revision, profile, plannerVersion, mode, startState = null })`、`planRevision({ revision, profile, plannerVersion, maximumSearchNodes, mode, startState = null })`；`mode` 必填 `preview | formal`。每条路线的 `score` 已携带 `fireMarginBucket`、`exposureDoseBucket`、`maximumBlockageRatioBucket`、`meanBlockageRatioBucket`与 `bucketProfileId`，实时层只消费这些核心已量化字段，不重新分桶。
- `PLANNER_PROFILE_V1_1` 固定为 `{ id:'planner-1.1-lexicographic', toleranceBucketAlgorithm:'floor-ratio-plus-epsilon-v1', fireMarginMinimumCellCount:1, exposureDoseBucketSize:0.01, maximumBlockageRatioBucketFloor:0.02, meanBlockageRatioBucketFloor:0.02, bucketBoundaryEpsilon:1e-9 }`；核心量化公式为 `Math.floor(value / size + epsilon)`。实时层不复制该公式，只用 `bucketProfileId` 验证同规则后比较已存四桶。
- `PlanningStartState = { currentPositions: Record<personId, {x,y}>, currentSimMs: number }`，位置使用归一化沙盘坐标；非零动态续跑必须恰好覆盖七人。
- `dist/core/simulation.mjs`: `scheduleSevenEvacuees({ revision, candidatesByPerson, profile, maximumSearchNodes, continuation = null, startState = null }): SchedulingResult`；`SchedulingResult = { selectedPlans, evacueeResults, metrics, optimalityStatus, diagnostics, continuation, startState }`，continuation 是仅供 Worker 使用且绑定 revision/planner/profile/规范化 startState 的不透明续搜状态。
- 规划 Worker 对每个 `PLAN_REVISION` 必须严格执行 `planRevision({ ..., mode, startState })` 恰好一次，再将其同一个 `candidatesByPerson` 和同一个 `startState` 传给 `scheduleSevenEvacuees({ ..., continuation:null, startState })` 恰好一次；不得另行调用 `generateRouteCandidates`、二次调度或再加 `currentSimMs`。
- `SimulationSnapshot` 的权威位置/时间是归一化的 `evacuees[].currentPosition` 与 `simTimeMs`；`currentGridCell` 只是可选渲染缓存。`planningStartStateFromSnapshot(snapshot)` 必须复制恰好七个 `currentPosition` 并加上 `snapshot.simTimeMs`，且绝不读 `currentGridCell`。
- `dist/core/simulation.mjs`: `createSimulationMachine({ runId, revision, schedule, profile, clock, idFactory })` 返回 `{ getSnapshot(), start(), pause(reason), markStale({ at, reason }), restore({ revision, schedule }), resume({ revision, schedule }), advance(deltaSimMs), replan({ revision, schedule, reasonCode }), finishFailed(reasonCode), reset({ revision, schedule }), subscribe(listener), dispose() }`。
- `dist/core/local-store.mjs`: `openLocalStore({ indexedDB, dbName = 'xiangxing-escape-v1.1' })` 返回 `putImage(imageRecord)`、原子 `putRevisionBundle({ revision, imageRecord })` 和 `putPlanRun`；bundle 写入校验 `revision.image.hash === imageRecord.hash`。

### Task 3: 单在途抽帧与“拍摄当前帧”统一 CandidateRevisionBundle 入口

**Files:**
- Create: `dist/live/camera-capture.mjs`
- Test: `tests/live/camera-capture.test.mjs`

**Interfaces:**
- Consumes: `HTMLVideoElement` 等价对象、Canvas 工厂、Task 1 profile、调度器、预分配的核心 `RevisionReservation`、worker-backed `PerceptionAdapter` 与核心 `createCandidateRevisionFromImage(...)`。
- Produces: `createCameraFrameSampler({ video, canvasFactory, clock, scheduler, profile, onFrame, onHeartbeat })`，返回 `start()`、`stop()`、`setProfile(profile)`、`captureCurrentFrame()`、`getStats()`。
- Produces: `captureCurrentFrameBundle({ sampler, reservation, requestId, parentRevision, detectedCorners = null, manualCorners = parentRevision?.calibration?.boardBounds ?? null, adapter, thresholdProfile, retainNormalizedFullOriginal = false, originalConsentAt = null, signal, onProgress, candidatePipeline = createCandidateRevisionFromImage }): Promise<CandidateRevisionBundle>`。
- 每个分析帧为 `{ frameId, capturedAt, width, height, decodedPhoto, source:'camera' }`；`decodedPhoto` 精确为 `{ orientedImageData, source: { fileName: 'camera-<frameId>.png', detectedMime:'image/png', byteLength, width, height }, release() }`。Canvas 产生实际 PNG 字节长度；`release()` 幂等。Wrapper 在调用核心 pipeline 前为释放责任方；交接调用发生后，核心 pipeline 独占责任并在成功、失败或 abort 路径精确调用一次，wrapper 不得在 `finally` 中再调用。
- Wrapper 必须先校验 reservation 的 `source === 'camera'`、parent/scene 与 `parentRevision` 一致，再把 reservation/requestId/decodedPhoto/corners/adapter/threshold/retain/consent/signal/progress 原样传给核心 pipeline。无 detectedCorners 时复用已确认 parent 的 `calibration.boardBounds`；两者都不存在时抛 `CAMERA_CALIBRATION_REQUIRED`。摄像头默认 `retainNormalizedFullOriginal:false`、`originalConsentAt:null`。

- [ ] **Step 1: 写出抽帧调度失败测试**

  使用假时钟断言高档每 500 ms、低档每 1,000 ms 分析一次；前一帧未完成时下一次 tick 只增加 `droppedFrames`，不排队；`stop` 后不再抽帧；每次成功帧都调用心跳。
