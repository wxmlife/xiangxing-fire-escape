# 巷行 V1.1 实施计划索引

**设计依据：** `docs/superpowers/specs/2026-10-02-v1.1-realtime-recognition-routing-design.md`

V1.1 被拆成三个可独立验收、按依赖顺序执行的子计划。任何后续阶段都复用前一阶段的不可变数据契约，不另建一套识别、道路或规划模型。

## 执行顺序

1. [本地核心实施计划](./2026-10-02-v1.1-local-core-implementation.md)
   - 13 个 TDD 任务。
   - 先交付无需登录即可使用的完整闭环：照片导入、自动候选识别、人工复核、道路净宽、严格词典序路线、七人仿真、历史和本地排行榜。
   - 冻结 `Scene`、`SceneRevision`、`RoutePlan`、`PlanRun`、`EvacueeResult`、Worker、IndexedDB 和规划器接口。

2. [实时摄像头与动态改路实施计划](./2026-10-02-v1.1-realtime-camera-implementation.md)
   - 10 个 TDD 任务。
   - 依赖本地核心的统一照片/感知管线、规划 Worker、仿真状态机和本地仓库。
   - 交付标准浏览器摄像头接入、当前帧拍照、基准配准、变化识别、防抖、最新修订优先、动态改路、断流 `STALE` 和真实设备验收门禁。

3. [可选云同步、团队共享与服务端排行实施计划](./2026-10-02-v1.1-cloud-sync-implementation.md)
   - 12 个 TDD 任务。
   - 依赖本地核心的数据契约；实时回放排行还依赖实时计划保存的完整修订时间线。
   - 交付游客优先的 CloudBase v3/PG 适配器、逐场景显式同步、不可变分支合并、团队角色、私有图片、可撤销分享、服务端重算排行和七天软删除。

## 共享接口冻结点

- 照片上传和摄像头“拍摄当前帧”统一调用 `createCandidateRevisionFromImage(...)`。
- 感知模型只输出版本化 `SceneRevision`；更换模型不得改变下游规划算法契约。
- 路线只消费已冻结修订，优先级固定为硬可行性 → 火源安全 → 堵塞 → 模拟用时/距离。
- 每个感知、规划、仿真、同步和排行结果都绑定精确 `revisionId` 与算法/参数版本。
- 本地 ULID 原样作为云端身份键；`sequenceNo` 只排序，不覆盖离线分支。
- 未登录、云端未配置或网络离线时，本地闭环必须继续完整工作。

## 验收边界

代码实现可以自动验证：

- 纯函数规划、三态掩膜、净宽下界、七人容量与确定性；
- IndexedDB 刷新恢复、导入导出、不可变历史和排行隔离；
- 摄像头假帧、配准、防抖、`STALE`、旧 Worker 结果隔离；
- PostgreSQL schema/RLS、云函数幂等、分享撤销、成绩篡改拒绝和删除生命周期；
- 390 px 移动端无横向溢出及游客本地流程。

以下门禁需要外部条件，不能由代码或模拟测试代替：

- 至少 30 张分层标注沙盘照片、至少 3 种设备，完成识别精确率/召回率验收；
- 使用实际技拓 UVC 摄像头完成设备、配准和 1/2 fps 延迟验收；
- 项目所有者创建上海 CloudBase PG 环境并提供环境 ID 与公开 Publishable Key；
- 完成安全来源、私有 Bucket、函数权限、微信资质、短信服务和真实双设备联调。

外部门禁未满足前，公开站点保留“候选结果需人工复核”和“云同步尚未配置”提示，但照片、本地规划、历史与本地排行仍可发布使用。

## 每阶段完成条件

每个阶段只有同时满足其计划中的全部测试、手工验收、文档和发布门禁，才进入下一阶段。提交应按任务保持小步、可回退；每个任务先写失败测试，再实现、复测和提交。所有阶段完成后再运行三份计划的联合回归，并通过 `publish.sh` 推送 GitHub、等待 GitHub Pages 工作流成功。
