# 巷行 V1.1：实时识别、动态逃生规划与历史排行设计

- 日期：2026-10-02
- 状态：设计方向已由用户确认，等待书面规范复核
- 适用产品：`xiangxing-fire-escape` 手机端沙盘模拟网站
- 安全边界：本产品只用于教学沙盘与算法演示，不作为真实火场中的认证疏散导航

## 1. 目标

V1.1 要让用户在不登录的情况下，通过技拓 USB 摄像头或手机照片导入新的城中村沙盘布局，自动得到可修正的场景识别结果，并为七位逃生者持续规划路线。

系统必须遵守以下不可互相抵消的优先级：

1. 路线必须可通行；穿越硬障碍、未知区、火源禁行区或净宽不足的路线直接淘汰。
2. 安全优先；在可通行路线中优先选择整条路径距离火源更远的路线。
3. 堵塞程度第二；安全等级相同时，优先选择剩余净宽更大、阻塞比例更低的路线。
4. 速度第三；安全和堵塞等级相同时，选择预计全员撤离用时更短、距离更短的路线。

V1.1 还要保存可命名、可版本化的历史场景和规划记录，并提供“七人全部撤离”的场景排行榜。基础功能无需登录；跨设备同步、团队共享和服务端校验排行榜需要用户按需登录。

## 2. 已确认的产品决策

- 输入图片是受控的同类沙盘照片，不承诺对任意真实街景或航拍图实现可靠识别。
- 自动识别在导入后立即运行，覆盖绿色门、火源、建筑、泡沫、车辆、杂物和出口候选。
- 自动结果是候选结果。用户可以移动、删除、新增、重画和改变类别；完成逐类复核后才生成正式规划记录。
- 低置信度区域进入 `UNKNOWN`，默认不可通行。
- 单个场景修订版内的火源位置和危险半径固定，不模拟烟气、材料、风向或火势蔓延；实时模式仍可识别火源的新增、移动或移除，并为变化生成新修订版。
- 技拓摄像头固定在沙盘正上方、完整覆盖沙盘四边，完成校准后不再移动。
- 系统保留“连接实时摄像头”和“拍照或选择图片”两个并列入口。
- 首次识别并人工确认后的地图成为场景基准；实时画面与基准比较固定建筑、移动障碍和火源变化。
- 无需登录即可使用全部本地识别、修正、规划、历史与本地排行功能。
- 用户只有在启用跨设备同步、团队共享或服务端校验云端排行时才登录；登录方式预留微信、手机号和邮箱。
- 排行榜以最后一位逃生者到达出口的时间为场景总撤离用时，只收录七人全部成功撤离的运行结果。
- 每个场景版本独立排名；总览只展示各场景的最佳成绩，不把不同尺寸和不同布局的原始秒数放进同一个竞争序列。
- 用户允许 V1.1 先提供明确标注的估算时间，不把估算结果描述为真实火场时间。

## 3. 非目标

V1.1 不包含以下能力：

- 真实建筑消防认证或面向真实火灾的现场指挥；
- 仅凭单张 RGB 图片判断某个出口在现实中是否安全；
- 动态烟气、温度、风向、材料燃烧和结构坍塌模拟；
- 多人同时拖动同一个标注对象的实时协同编辑；
- 浏览器直接读取 RTSP 等网络摄像头协议；
- 在缺少物理标尺时输出伪装成厘米或米的测量值；
- 用一个加权总分让距离优势抵消火源风险或通行宽度不足。

## 4. 总体架构

V1.1 使用“本地感知与规划、可选云端同步”的架构。

```text
实时 USB 摄像头 ─┐
                  ├─> 图像质量检查与俯视配准
照片/相册上传 ────┘
                              ↓
                      本地自动识别 Worker
                              ↓
             SceneRevision（候选、置信度、掩膜、版本）
                              ↓
                    人工图层复核与修正
                              ↓
               保守占据图 + 道路图 + 火源距离场
                              ↓
             词典序路线规划 + 七人联合时序仿真
                              ↓
           当前总路线 / 七条分路线 / 改路原因 / ETA
                              ↓
                  IndexedDB 本地版本与历史
                              ↓（按需登录）
       CloudBase PostgreSQL / 私有对象存储 / 团队共享 / 排行
```

前端继续部署在 GitHub Pages。浏览器端不保存任何管理员密钥；未配置云端时，所有本地功能仍须完整可用。

### 4.1 模块边界

- `input`：照片解码、摄像头连接、设备切换、断流与页面前后台状态。
- `calibration`：画面质量、沙盘边界、俯视配准、基准图和坐标变换。
- `perception`：起点、出口、火源、障碍、道路与未知区检测；实现可更换。
- `scene`：验证并冻结 `SceneRevision`，保存人工修正与模型版本。
- `road-network`：从可通行区生成道路骨架、路口、基准宽与当前净宽。
- `routing`：严格执行安全、堵塞、时间三个层级的候选筛选。
- `simulation`：为七人分配路线、路段容量和出口时隙，计算估算到达时间。
- `persistence`：IndexedDB 场景、版本、图片、运行记录和设置。
- `sync`：登录、团队、云端版本同步、冲突检测和分享。
- `ui`：输入选择、识别复核、实时状态、线路视图、历史与排行榜。

模块之间通过版本化数据结构通信。规划器不引用具体颜色阈值、视觉模型或摄像头 API，因此以后更换识别模型时，规划和历史数据格式保持稳定。

图像识别和规划默认运行在普通 Web Worker 中，主线程只负责视频预览和界面绘制。实现不得依赖 `SharedArrayBuffer` 或浏览器跨域隔离头才能工作；不支持 Worker/OffscreenCanvas 的设备降级到较低识别频率，而不是阻塞页面。

## 5. 核心数据模型

### 5.1 Scene

`Scene` 是用户命名的历史场景容器，不与某一张图片或某一次规划混为一体：

```js
{
  sceneId,
  name,
  description,
  tags,
  ownerScope: 'local' | workspaceId,
  currentRevisionId,
  baselineRevisionId,
  createdAt,
  updatedAt
}
```

### 5.2 SceneRevision

每次确认地图、有效实时变化或人工修正都会生成带递增编号的不可变场景修订版。实时修订先存在内存环形缓冲区；只有基准确认、人工修改、触发改路、用户手动保存或正式规划运行所引用的修订版才持久化，避免按视频帧无限增长历史：

```js
{
  schemaVersion: '1.1',
  sceneId,
  revisionId, // 全局 ULID，不使用仅本机递增整数
  sequenceNo, // 场景内排序提示，不作为身份键
  parentRevisionId,
  capturedAt,
  source: 'camera' | 'upload' | 'manual-edit',
  image: { hash, width, height, thumbnailRef, originalRef },
  calibration: {
    homography,
    boardBounds,
    quality,
    scaleMode: 'estimated' | 'measured',
    mmPerPixel: null | number
  },
  perception: { recognizerId, modelVersion, thresholdProfile },
  masks: {
    width,
    height,
    blockedRLE,
    unknownRLE,
    roadRLE
  },
  obstacles: [{ id, polygon, class, confidence, uncertainty, source, reviewed }],
  fires: [{ id, x, y, hardRadius, riskRadius, confidence, uncertainty, reviewed }],
  starts: [{ id, personNo, x, y, confidence, source, reviewed }],
  exits: [{ id, code, x, y, width, confidence, source, reviewed }],
  roads: [{
    id,
    centerline,
    corridor,
    widthProfile: [{ offset, baseWidth, measuredClearWidth, clearWidthLowerBound, blockageRatio }],
    bottleneckOffset,
    minimumClearWidthLowerBound,
    maximumBlockageRatio,
    lengthWeightedMeanBlockageRatio,
    status,
    blockerIds
  }],
  review: { starts, exits, fires, obstacles, completedAt, completedBy },
  edits: [{ id, operation, objectId, before, after, createdAt }]
}
```

掩膜是障碍边缘的权威表达，导出时使用 RLE 压缩。人工矩形、多边形和画笔是覆盖层；规划网格降采样时采用保守规则：源区域内只要存在硬障碍，该格即为硬障碍；否则只要存在未知像素，该格即为未知；全部为高置信道路时才为可通行。

### 5.3 RoutePlan

```js
{
  sceneId,
  revisionId,
  plannerVersion,
  simulationProfileVersion,
  personId,
  status: 'safe' | 'blocked' | 'stale',
  exitId,
  pathEdges,
  score: {
    minimumFireMargin,
    exposureDose,
    maximumBlockageRatio,
    lengthWeightedMeanBlockageRatio,
    estimatedArrivalSimMs,
    distanceUnits
  },
  reasonCode,
  computedAt
}
```

每条结果必须绑定精确的场景修订版、识别器版本、规划器版本和仿真参数版本，保证历史记录可复现。

### 5.4 PlanRun 与 EvacueeResult

一次正式运行使用组级记录，避免把七条互不关联的路线误当成同一场仿真：

```js
{
  runId,
  sceneId,
  mode: 'static' | 'live' | 'replay',
  baselineRevisionId,
  startRevisionId,
  endRevisionId,
  revisionTimeline: [{ simulationTimeMs, revisionId, eventType, routePlanHash }],
  scenarioScriptHash,
  plannerVersion,
  simulationProfileVersion,
  reviewCompleted: true,
  allEvacuated,
  optimalityStatus: 'proven' | 'provisional',
  status: 'completed' | 'failed' | 'stale',
  totalEvacuationSimMs,
  meanArrivalSimMs,
  startedAt,
  completedAt,
  resultHash
}
```

每个 `EvacueeResult` 以 `(runId, personId)` 为身份键，保存路线、出口、模拟行走时间、模拟排队时间、模拟到达时间和受阻原因。静态排行榜身份键为 `(sceneId, startRevisionId, plannerVersion, simulationProfileVersion)`；动态回放排行榜还必须加入相同的 `scenarioScriptHash`。只有完全相同的键才进入同一张榜。实时运行引用的全部修订版和路线哈希都必须持久化，服务端才能按时间线重放。

跨设备离线编辑时，`revisionId` 使用全局 ULID，父链引用全局 ID；`sequenceNo` 只用于界面排序。两台设备产生相同序号时保留两个分支，不以序号覆盖任何版本。

## 6. 输入与校准流程

### 6.1 受支持输入契约

自动识别的受支持条件是：沙盘完整可见、相机基本俯视、道路与模型未被人体大面积遮挡、照明不会使大面积区域过曝。照片入口接受 JPEG、PNG 和 WebP，单文件最多 20 MB、解码后最多 2400 万像素；HEIC 只在浏览器能够原生解码时接受，否则提示用户转换为 JPEG/PNG，不把解码失败当成识别失败。

统一火源外观为带黑白高对比外框的红橙色火焰图案，校正后宽度应位于沙盘宽度的 2%–8%。不符合该外观的红色车辆或玩具只可成为低置信火源候选，不能自动确认；非标准火源必须由用户人工标记或确认。

USB 实时模式的首要支持矩阵为桌面 Chrome/Edge，以及被操作系统暴露为标准视频输入的技拓摄像头。手机端保证照片/相册/内置摄像头拍照入口；只有移动操作系统与浏览器实际列出外接摄像头时，才开放 USB 实时选项。

### 6.2 实时摄像头模式

1. 用户点击“连接实时摄像头”；浏览器此时才请求摄像头权限。
2. 授权后列出操作系统暴露的摄像头，优先使用用户选择的技拓设备。
3. 预览保持约 15–30 fps；识别默认以 640×480、2 fps 抽帧运行，低性能设备自动降到 480×360、1 fps。
4. 用户确认沙盘边界和基准地图后进入实时规划。
5. 用户可以点击“拍摄当前帧”，把技拓摄像头画面冻结成普通照片场景；冻结后使用与手机上传完全相同的识别、修正和保存流程。
6. 摄像头拔出、轨道结束、页面进入后台或帧超过两秒未更新时，状态变为 `STALE`，停止宣称当前路线实时安全。
7. 回到前台或恢复设备后重新验证画面配准；机位变化超过容差时要求重新校准基准。

如果技拓摄像头没有被操作系统暴露为标准视频输入，网页不尝试绕过系统驱动；用户改用内置摄像头或照片上传入口。

### 6.3 照片模式

1. 用户选择相册图片、相机拍照或桌面文件。
2. 浏览器检查真实可解码格式、像素数量、模糊度、曝光和图像方向。
3. 系统尝试自动识别沙盘边界并转换为俯视坐标；置信度不足时显示四角修正工具。
4. 完成自动识别后立即显示候选地图和预览路线。
5. 每次人工编辑都会创建新修订版并重新规划；照片模式不会被标记为“实时监测”。

### 6.4 估算与测量尺度

用户已允许先估算时间。未提供物理标尺时，系统使用版本化的“模拟时间参数”，所有结果明确显示为“模拟秒”：

- 规划网格固定为 108 列，高度按校正图比例确定；
- 每个正交网格步默认 0.35 模拟秒，对角步乘以 `√2`；
- 同一场景版本的所有运行使用相同参数；
- 参数变化会生成新的规则版本，旧成绩不会与新成绩混排；
- 未测量场景之间不比较真实物理速度。

V1.1 同时提供可选的“两点标尺”入口：用户在图片上点击两点并输入实际距离，即可生成新的测量版修订，按米和配置的步行速度计算。用户跳过标尺时继续使用模拟秒；补充标尺不会篡改原有估算记录。

## 7. 自动识别与人工复核

### 7.1 自动识别策略

V1.1 初版使用浏览器本地混合识别，并提供稳定的 `PerceptionAdapter` 接口以便后续接入专用 ONNX 模型：

- 绿色门：HSV/Lab 颜色范围、连通区域、尺寸与邻近建筑边缘约束。
- 火源：优先识别受支持输入契约中的统一火焰图案，结合红橙候选、黑白外框、局部颜色分布、形状与尺寸约束；输出火源中心和两个可编辑半径。只满足颜色条件的车辆或玩具进入待确认候选。
- 白色泡沫：识别低饱和高亮长条及其连续边界。闭合泡沫边界及其内部整体填充为硬障碍；边界存在未确认断口时，断口和内部先标为 `UNKNOWN`，不得把内部自动开放为道路。高光噪声也进入未知区。
- 固定建筑：沙盘基准帧中的闭合轮廓、边缘密度和大面积非道路区域。
- 动态障碍：当前帧与已配准基准图的差异、局部轮廓与占地掩膜。
- 道路：只把高置信、连通且不属于障碍/未知的区域定义为道路。
- 出口：在沙盘边界上寻找满足最低净宽的道路开口，只生成候选，不能凭视觉直接声明现实出口安全。

自动识别必须输出置信度与误差范围，而不是输出一个未经说明的准确率百分比。不同识别模型携带独立版本、类别表、阈值档案和文件哈希，换模型时不得沿用未经校准的旧阈值。

### 7.2 人工复核

复核界面按图层展示起点、出口、火源、硬障碍、未知区和道路。用户可以：

- 接受或删除自动候选；
- 拖动绿色门、出口和火源中心；
- 调整火源禁行半径和风险半径；
- 使用画笔、矩形或多边形补充障碍；
- 使用“开放道路”工具将误判的未知/障碍区域恢复为道路；
- 撤销、重做并查看每项修改来源。

低置信候选按连通组件和对象列出，而不是要求用户逐像素确认；用户可以逐项处理，也可以在查看整层叠加后执行“确认本层全部保持不可通行”。批量确认只能维持 `UNKNOWN/blocked`，不能一键把未知区域全部开放为道路。

正式确认门槛为：恰好七个已确认起点、至少一个已确认出口、火源状态已确认、所有低置信候选组件已处理、障碍图层已复核、起点与出口均不位于硬障碍或未知区。未满足门槛时只允许预览，不允许生成正式排行榜记录。

## 8. 道路宽度与堵塞判定

基准地图从结构道路走廊中提取道路骨架和路口图。每条道路保存沿中心线采样的结构宽度剖面 `Wbase(s)`；它由固定建筑、泡沫和边界之间的道路全宽得到，不把车辆、纸箱等可移动障碍算进道路边界。首张图中已经存在动态障碍时，系统根据障碍两侧可见的固定边界插值结构走廊，并把插值误差计入不确定度；无法可靠插值时要求用户用“道路走廊”工具补画，不能把当前被占用的窄宽误当成基准宽。当前帧加入动态障碍后，通过距离变换和道路横截面扫描得到当前净宽剖面 `WclearMeasured(s)`，再扣除识别与配准误差：

```text
WclearLB(s) = WclearMeasured(s) - 识别/配准误差
blockageRatio(s) = clamp(1 - WclearLB(s) / Wbase(s), 0, 1)
```

每条道路保存宽度剖面、瓶颈位置、`min(WclearLB)`、最大堵塞率和按道路长度加权的平均堵塞率，而不是只保存一个来源不明的宽度标量。道路状态为：

- `OPEN`：净宽充足，堵塞低于限制阈值；
- `RESTRICTED`：仍可通行，但存在明显阻塞或降速；
- `BLOCKED`：`WclearLB` 小于人员有效宽度加双侧安全余量；
- `UNKNOWN`：道路或障碍识别不确定，按不可通行处理。

系统比较的是道路被占用后的剩余横截面，而不是只比较障碍面积。因此即使所有道路都有障碍，也能优先选择仍然更宽、最严重堵塞比例更低的路线。

无物理尺度时，页面显示“网格”和“沙盘宽度百分比”；有尺度时才显示厘米或米。

## 9. 严格优先级动态规划

现有 V1.0 的距离、火源风险和拥堵加权总和不能保证用户要求的严格优先级。V1.1 改为词典序多阶段规划：

### 9.1 硬约束

规划前删除硬障碍、`UNKNOWN`、火源禁行圈和净宽不足的道路。起点或出口落入这些区域时直接报告受阻，不跨墙吸附到其他位置。如果不存在安全路径，返回 `BLOCKED`，绝不降级选择危险路线。

### 9.2 安全层

对每条候选路线计算：

```text
fireMargin = 整条路线距离任一火源安全边界的最小距离 - 测量误差
```

先用 maximin（最宽路径）搜索得到每位逃生者可达到的最佳 `fireMargin`。安全容差定义为 `fireEpsilon = max(1 个规划格, 火源位置不确定度 + 配准误差)`；只有 `fireMargin >= 最佳值 - fireEpsilon` 的边可以进入下一层。

安全层内的第二指标是累计暴露：对路径每段按长度积分其位于火源风险半径中的归一化风险，多个火源取叠加后上限为 1。由此，当所有候选路线共享同一个靠近火源的起点时，系统仍会选择更快离开风险区域的方向。差异不超过误差容差时视为同级，避免一像素变化导致反复换路。

### 9.3 堵塞层

在安全层保留的子图中，用 minimax 搜索得到每位逃生者可达到的最小“最严重堵塞率”。堵塞容差为 `blockageEpsilon = max(0.02, 道路宽度不确定度 / 结构基准宽度)`；只有最大堵塞率不超过最佳值加容差的边可以进入时间层。随后比较按路段长度加权的平均堵塞率。由此保证“堵塞少”严格优先于“距离短”。

### 9.4 时间层

只在安全与堵塞均属同级的子图中，为每位逃生者按稳定的起点 ID 与出口 ID 顺序生成最多 8 条无环候选路线，再由七人时隙调度器最小化全员撤离时间。每位逃生者都必须保持自己的安全阈值与堵塞阈值，不能为了降低全组时间牺牲某个人的高层级指标。路径距离仅作为最终平局条件。

### 9.5 确定性比较键

单人候选路线使用以下比较键，前项完全优先于后项：

```text
(
  -minimumFireMarginBucket,
  exposureDoseBucket,
  maximumBlockageRatioBucket,
  lengthWeightedMeanBlockageBucket,
  estimatedArrivalSimMs,
  distanceUnits,
  stablePathHash
)
```

`Bucket` 按上述误差容差离散化。七人组合先按七人最差到最好排序后的安全桶向量比较，再比较同样排序的堵塞桶向量，最后比较全员撤离时间、平均到达时间、总距离和稳定组合哈希。该定义保证输入人员数组顺序不会改变结果，并使每个测试场景只有一个确定输出。

### 9.6 搜索预算与安全降级

七人组合不直接穷举最多 `8⁷` 个方案。调度器按“候选最少者优先、稳定人员 ID 次序”展开确定性分支限界搜索，使用剩余人员的最早可能到达时间作为 makespan 下界，并缓存被占用路段/时隙的支配状态。实时重算最多展开 `simulationProfile.maximumRealtimeSearchNodes` 个节点。

达到实时节点上限时：

1. 若已有满足每个人安全与堵塞阈值的组合，显示确定性的最佳当前组合并标记“安全临时方案，仍在优化”；
2. 若旧计划对最新修订版仍满足全部硬约束和原有安全/堵塞桶，可暂时沿用并标记“正在重算”；
3. 否则立即隐藏旧路线并显示“正在重算/暂无确认安全路线”，绝不退到较低安全桶或较高堵塞桶；
4. Worker 在后台继续搜索到证明最优或穷尽候选。只有 `optimalityStatus: 'proven'` 的静态或可回放运行可以进入排行榜。

正式测试分别记录候选生成、单人分层搜索和七人调度的节点数与耗时，覆盖 8 条候选/人的最坏配置。

## 10. 实时变化与自动改路

摄像头帧先配准到相同俯视坐标，然后生成新的全局 `revisionId` 和场景内递增 `sequenceNo`。识别和规划在 Worker 中执行；旧修订版的晚到结果不得覆盖新地图。

安全侧使用不对称防抖：

- 高置信新火源或新障碍落在活动路线：单次识别即可立即封闭和重新规划；
- 中置信新阻断：至少持续 500 ms 且连续两次采样出现后封闭；
- 障碍消失或火源消失：2 fps 档至少连续稳定两秒，1 fps 档至少连续稳定三秒才重新开放；
- 当前路线变危险或净宽不足：绕过普通防抖立即重算；
- 其他变化合并约 250 ms，最多每秒重算 2–4 次；
- 感知结果确认存在更高安全桶路线时立即切换；安全桶相同、堵塞桶改善超过测量误差时切换；安全和堵塞桶都相同时，只有预计用时改善至少 10% 且稳定一秒才切换，防止线路闪烁。

每次改路记录 `revisionId`、触发原因和变化前后的路线指标。界面显示“发现新火源”“通道净宽不足”“选择堵塞更少道路”“预计用时降低”或“画面已过期”等可解释原因。

性能预算按实际采样档位区分：2 fps 档中，高置信危险变化到封路的 p95 不超过 1.5 秒，中置信危险不超过 2 秒；1 fps 档中对应上限分别为 2 秒和 3 秒。界面必须展示当前档位及其最大更新延迟，不能在 1 fps 设备上承诺 1.5 秒完成两帧确认。

## 11. 七人联合撤离仿真

七位逃生者是虚拟仿真对象，摄像头不追踪真人位置。一次运行使用确定状态机：

```text
READY -> RUNNING <-> PAUSED
           |
           +-> STALE -> PAUSED
           |
           +-> COMPLETED | FAILED
```

- “开始仿真”从时刻零启动单调模拟时钟；
- “暂停”冻结时钟和七人位置，但实时感知可以继续更新地图；
- “继续”先对最新修订版重规划，再恢复推进；
- “重置”结束当前运行并创建新的 `runId`，不得改写旧成绩；
- 摄像头过期时进入 `STALE` 并自动暂停；
- 画面恢复并重新通过配准检查后，`STALE` 回到 `PAUSED`，必须由用户继续或重置；
- 七人全部到达进入 `COMPLETED`；任一人确认无安全路线且用户结束运行时进入 `FAILED`。

七位逃生者默认在模拟时刻零同时出发。每人先获得满足安全和堵塞层的候选路线，再由时隙调度器分配道路和出口容量：

- 道路有效通行人数由 `WclearLB / 最低人员通行宽度` 的保守整数结果决定；
- 单通道不允许同一时隙中出现相向或重叠冲突；
- `RESTRICTED` 路段按堵塞比例降低移动速度；
- 出口默认每 1.0 模拟秒放行一人；
- 排队等待计入个人到达时间；
- 全员撤离时间是七个到达时间的最大值；
- 实时改路从各人的当前模拟网格位置继续，不从起点重新计时；当前点仍可通行时只替换后续路径，不把人员吸附到墙体另一侧；当前点被新火源或障碍覆盖时，人员冻结并报告 `BLOCKED_AT_CURRENT_POSITION`，等待地图恢复或用户结束运行，绝不瞬移到最近自由格；
- 输入人员数组顺序不得改变最终出口分配和全员撤离时间。

估算参数保存在 `simulationProfile` 中并带版本号。页面同时显示每人的行走时间、排队时间、到达时间，以及全员最后到达时间。

### 11.1 SimulationProfile v1.1 默认值

估算模式使用以下完整、版本化的参数，确保同一输入能够复现：

```js
{
  id: 'sim-1.1-estimated',
  planningGridWidth: 108,
  effectivePersonWidthRatio: 0.046,
  orthogonalStepSimMs: 350,
  diagonalStepMultiplier: Math.SQRT2,
  timeSlotSimMs: 250,
  exitServiceSimMs: 1000,
  openBlockageMaximum: 0.15,
  restrictedSpeedMinimumMultiplier: 0.35,
  maximumCandidatesPerPerson: 8,
  maximumRealtimeSearchNodes: 20000
}
```

`effectivePersonWidthRatio` 是人员身体宽度、双侧安全余量和识别误差的合并模拟值，不伪装成真实人体尺寸；在 108 列网格下按保守奇数取整得到 5 格。道路净宽低于该值时为 `BLOCKED`；堵塞率低于 15% 且净宽合格时为 `OPEN`，其余可通行道路为 `RESTRICTED`。限制路段的速度倍率为：

```text
speedMultiplier = max(0.35, 1 - 0.65 × blockageRatio)
```

估算模式中，标准火源的默认硬禁行半径为“火源候选半径的 1.5 倍加识别误差”与“沙盘较短边的 4%”两者较大值，风险半径为硬禁行半径的 4 倍；两者必须在复核界面可调。风险半径内的单位风险为：

```text
risk(d) = clamp((riskRadius - d) / (riskRadius - hardRadius), 0, 1)²
```

其中 `d` 是到火源中心的距离；硬禁行半径内不计算风险分，而是直接禁止通行。

测量模式使用 `sim-1.1-measured`：默认模拟身体宽 0.55 m、两侧各 0.15 m 安全余量、有效最低净宽 0.85 m、无堵塞步行速度 1.0 m/s，其他堵塞、出口和候选规则与估算模式一致。这些数值均是教学仿真假设，用户修改任一值都会产生新的 `simulationProfileVersion`，旧成绩不会与新成绩混排。

## 12. 本地历史、账号同步与多人共享

### 12.1 无登录本地模式

IndexedDB 保存：

- 用户命名的场景；
- 原图或压缩后的本地图片；
- 每次确认形成的场景版本；
- 自动识别对象、人工修改和复核状态；
- 正式与失败规划记录；
- 每人路线和估算时间；
- 本地排行榜。

用户可以导出一个包含场景 JSON、缩略图和版本信息的备份包，也可以重新导入。清除浏览器数据会删除未同步记录，界面必须明确提示。

应用启动时请求浏览器持久存储能力，并展示已用空间估算。实时内存修订保留最近 120 个；每个场景最多自动保留最近 200 个事件检查点，超过后只合并未被正式运行引用的连续感知差分，绝不自动删除基准、人工确认版本或正式运行引用版本。达到预计配额 80% 时停止保存新的原始帧，只保存掩膜差分和缩略图，并提示用户导出或删除记录。

### 12.2 可选登录与云端模式

云端优先采用上海地域的 CloudBase PostgreSQL，表结构包括：

- `profiles`
- `workspaces`
- `workspace_members`
- `scenes`
- `scene_versions`
- `scene_objects`
- `plan_runs`
- `route_results`
- `audit_events`

用户点击“跨设备同步”或“邀请成员”时才登录。登录后把本地 UUID 和图片哈希与云端记录合并，避免重复上传；冲突时保留两个不可变版本，不静默覆盖。

云端激活依赖项目所有者在腾讯云创建 CloudBase 环境并提供环境 ID，配置 PostgreSQL、对象存储、认证、Web 安全域名、云函数和回调域名。微信登录还需要可用的微信应用资质；手机号登录需要短信服务、模板和相应费用。代码库只交付数据库迁移、行级策略、云函数、配置模板和部署检查，不提交真实环境 ID 之外的私密凭证。未满足这些外部前置条件时，游客本地功能仍构成可运行版本，但跨设备、微信/手机号登录和云端排行明确显示“尚未配置”。

浏览器通过受支持的 Web SDK、受行级策略保护的数据 API 和认证云函数访问数据，不建立直连 PostgreSQL 的数据库连接。排行榜写入、成员权限变更和分享令牌创建只能通过认证云函数或具备等价服务端校验的 RPC 完成。

团队角色为：

- 所有者：管理成员、场景、分享与删除；
- 编辑者：上传、修正、确认并生成新版本；
- 查看者：查看历史和路线，不能修改。

V1.1 采用异步协作，不做多人实时共同拖动标注。所有场景默认私有；所有者可以生成可撤销的只读分享链接。

### 12.3 安全要求

- 原图使用私有对象存储，通过短时效访问地址读取；
- 浏览器仅持有公开客户端配置，管理员密钥只能存在于云函数环境；
- 数据库和对象存储按团队成员关系执行行级访问控制；
- 上传图片限制格式、体积和像素数，保存前重新编码并移除 EXIF/GPS；
- 默认不上传实时视频帧，只同步用户明确保存的场景版本和快照；
- 云端排行榜记录由可信函数重算或校验，客户端不能直接写成绩。

默认只保存和上传裁剪、俯视校正、重新编码后的沙盘区域，不保存包含人员或办公环境的完整原图；用户若选择保留完整原图，界面必须在保存或上传前单独说明。云端上传是显式操作，不能因用户打开登录页而自动上传本地照片。

只读分享令牌至少包含 128 位随机熵，默认七天过期，并可由所有者立即撤销；分享页面使用短时签名图片地址且禁止列出存储目录，不存在稳定公开原图 URL。授权查看者的浏览器在有效期内会取得短时图片地址，因此产品只承诺地址短时、受控和不可枚举，不承诺客户端从未见到地址。

认证会话使用 CloudBase SDK 支持的存储与刷新机制；页面禁止注入用户提供的 HTML，采用严格 CSP、自托管运行时代码和输出转义降低 XSS 窃取令牌风险。用户可以导出数据、撤销分享、删除自己的本地场景、删除云端场景、删除已保存原图并注销账号；团队删除权限只属于所有者。云端删除采用 7 天可恢复软删除，期满后清除数据库对象和存储文件。

云端“服务端校验”只表示服务端使用已保存的场景输入与指定算法版本重算一致，不代表现场照片、人工标注或火灾状态经过消防机构认证。

云端未配置、网络不可用或用户未登录时，本地使用不得被阻塞。

## 13. 历史与排行榜

历史页按场景卡片展示名称、缩略图、最近更新时间、版本数、识别状态、最佳全员撤离时间和同步状态。进入场景后可以查看：

- 基准地图与当前版本；
- 每次自动识别和人工修正；
- 每次规划的总路线与七条分路线；
- 火源距离、道路堵塞和改路原因；
- 七人个人到达时间和全员撤离时间；
- 使用的识别器、规划器与仿真参数版本。

排行榜规则：

1. 只收录 `allEvacuated === true`、`optimalityStatus === 'proven'` 且已完成人工复核的正式运行；
2. 每个场景版本独立排行；
3. 按全员撤离时间升序；
4. 同分时依次比较七人平均到达时间和服务端记录时间；
5. 失败运行保留在历史中，但不进入成功榜；
6. 未登录的本地成绩标记为“本地估算”；经云端重算一致后标记为“服务端校验”，不使用容易被理解为现实安全认证的“已验证”字样；
7. 未经事后复核的实时运行只进入历史，不进入正式榜；用户可以把完整事件时间线冻结为“动态回放脚本”，逐项复核变化后重新运行，只有相同 `scenarioScriptHash` 的回放结果才能互相排名；
8. 总览按当前选定的 `plannerVersion + simulationProfileVersion` 展示每个场景的最佳成绩；切换规则版本时分组展示，不跨规则取一个混合“最佳”；
9. 不跨不同场景直接比较原始秒数。

## 14. 手机端交互设计

首页提供两个同等明显的入口：

- “连接实时摄像头”
- “拍照或上传图片”

主操作流程分为四步：

1. **导入**：选择输入方式，检查画面质量和沙盘边界。
2. **自动识别**：显示逐类进度和候选数量，完成后进入图层预览。
3. **复核修正**：通过底部工具栏切换道路、障碍、火源、起点、出口与擦除；支持撤销/重做。
4. **规划监控**：显示总路线、七条分路线、当前优先级指标、实时更新时间和改路原因。

实时模式顶部状态条显示：摄像头名称、实际分辨率、识别频率、端到端延迟、画面新鲜度和基准是否对齐。任何 `STALE`、权限拒绝或配准失败状态都以显著警告替代“路线安全”提示。

地图支持图层开关：原图、道路、障碍、未知区、火源距离、道路宽度、堵塞率和路线。点击道路可查看基准宽、剩余宽、堵塞比例、障碍来源和置信度；点击路线可查看选择原因。

历史和排行榜作为底部导航中的独立页面。390 px 宽屏幕不得出现横向页面滚动，地图编辑时提供显式“编辑锁定/页面滚动”切换，避免画布吞掉整个页面手势。

## 15. 错误处理与降级

- **摄像头不兼容**：说明系统未暴露视频设备，并展示照片上传入口。
- **权限被拒绝**：不循环请求；提供浏览器权限说明和照片模式。
- **摄像头断流**：立即停止实时安全结论，保留最后画面供查看但标记过期。
- **图片解码失败**：终止分析并释放对象 URL，不启动永久轮询。
- **画面模糊、过曝或沙盘不完整**：阻止正式确认，允许重新拍摄或继续作为低置信预览。
- **自动识别超时或 Worker 崩溃**：终止当前任务、保留输入图并允许重试或纯手工标注。
- **没有安全路线**：明确显示受阻人员与原因，不放宽火源或宽度规则。
- **云端离线**：写入本地待同步队列；恢复后按不可变版本合并。
- **多人版本冲突**：同时保留两个版本，要求用户选择继续使用哪个版本，不自动覆盖。
- **存储空间不足**：保留场景数据和缩略图，提示用户导出或删除原图副本。

## 16. 测试与验收标准

### 16.1 识别质量

- 建立至少 30 张受控沙盘测试图，覆盖不同布局、日间室内光照、阴影、轻微倾斜、不同障碍位置和至少三种支持的拍摄设备；同一连拍序列不得同时进入调参与验收集合。
- 分别报告硬障碍召回率、可通行区精确率、各类别 IoU、火源/绿色门/出口候选的精确率与召回率，不用单一“总体准确率”掩盖漏障风险。
- 在验收集合中，硬障碍召回率不得低于 95%，可通行区精确率不得低于 98%；不满足时相关区域必须进入 `UNKNOWN`，不得自动标为道路。
- 自动误开放道路像素占全部自动开放道路的比例不得超过 2%；任何导致路径穿越真值障碍的误开放样本都按发布阻断问题处理，而不是被总体平均值掩盖。
- 保守净宽下界不得比人工真值净宽高估超过 1 个规划格；道路瓶颈位置误差不超过 2 个规划格。无法满足时该路段必须进入 `UNKNOWN`。
- 统一火源外观的验收集合中，火源召回率不得低于 95%；漏检样本必须由质量门禁或人工复核拦截，不能生成正式排行记录。
- 七个绿色门与已知出口的候选漏检必须在复核摘要中逐项暴露，不能因候选数量不足而静默补点。
- 最终端到端安全指标为：所有已确认测试场景中，规划路径与人工真值硬障碍、未知区或火源禁行区的相交次数为零。

### 16.2 规划正确性

- 近火、短且畅通的路线与远火、较长且略堵的路线同时存在时，必须选择远火路线。
- 火源安全等级相同时，短路堵塞 40%、长路堵塞 10% 时必须选择后者。
- 安全和堵塞同级时才允许选择预计用时更短的路线。
- 净宽 4 格、最低需求 5 格时必须判定 `BLOCKED`；识别误差扣除后的下界不足也必须封路。
- 所有道路都有障碍时，按最严重堵塞比例和剩余宽度选择，不按障碍总面积选择。
- 路径与硬障碍、未知区及火源禁行区的相交次数必须为零。
- 108、216、320 列规划分辨率下，通行与封闭判定必须一致。
- 感知模型输出相同 `SceneRevision` 时，更换模型版本不得改变规划结果。
- 同一 `SceneRevision`、`simulationProfileVersion` 和规划器版本重复运行必须产生相同路径哈希与模拟用时。
- 出现更高安全桶路线时，即使预计用时更长也必须优先改路；安全同级后才比较堵塞，二者同级后才应用 10% ETA 防抖。
- 七人候选达到 8 条/人的压力场景中，分支限界不得枚举全部组合；触发节点上限时只能返回满足高层级约束的临时方案或“暂无确认安全路线”。

### 16.3 实时性与稳定性

- 固定沙盘中移动障碍后，2 fps 档高置信危险变化到新路线显示的 p95 延迟不超过 1.5 秒，中置信不超过 2 秒；1 fps 档对应上限为 2 秒与 3 秒。
- 新火源出现在活动路线附近时，高置信单次采样立即封闭，中置信至少持续 500 ms 且不超过两次采样封闭。
- 障碍移走后至少稳定约两秒才开放。
- 阈值附近的噪声帧不得导致路线反复闪烁。
- 摄像头断流或结果超过两秒未更新时，界面必须进入 `STALE`。
- 新修订版出现后，旧 Worker 结果不得覆盖新结果。

### 16.4 七人仿真与排行

- 改变七位逃生者在数组中的输入顺序，不得改变出口分配和全员撤离时间。
- 单人宽窄道不得在同一时隙安排冲突通行。
- 全员撤离时间必须等于七人到达时间的最大值。
- 任意一人受阻时，该运行不得进入成功榜。
- 不同场景版本、规划器版本或仿真参数版本不得混入同一排行榜。
- 客户端伪造的云端成绩必须被拒绝。
- 实时运行按保存的 `revisionTimeline` 重放必须得到相同结果哈希；没有完整时间线或未复核事件的运行不得进入动态回放榜。

### 16.5 输入、历史与移动端

- 对同一张校正图作为视频帧和上传照片输入时，语义对象数量、位置、净宽与最终规划结果应在识别误差容差内等价，不要求压缩噪声下逐像素完全相同。
- 未登录时刷新页面可恢复本地场景；登录后另一设备可读取已同步版本。
- 本地与云端冲突必须保留两个版本。
- 两台离线设备生成相同 `sequenceNo` 时，全局修订 ID 不得碰撞，父链和两个冲突分支都必须保留。
- 未经授权不能读取原图，且不存在稳定或可枚举的公开原图 URL；只读分享不得泄露邮箱、手机号或 EXIF。
- 过期或撤销的分享令牌必须立即失效；账号注销和七天软删除期结束后，相应数据库记录与存储对象必须不可读取。
- 390 px 手机视口无横向页面溢出，照片入口和主要修正操作单手可达；USB 实时入口只在设备被操作系统和浏览器暴露为视频输入时验收。
- 摄像头不可用、权限拒绝、图片损坏和存储不足均存在可操作的降级路径。

## 17. 实施顺序

所有阶段共同组成 V1.1，但按以下依赖顺序开发和验证：

1. 拆分现有单文件逻辑，建立 `SceneRevision`、版本化参数和 IndexedDB 数据层。
2. 完成照片双入口、质量检查、候选识别和分层人工复核。
3. 建立道路图、净宽/堵塞率计算和严格词典序规划。
4. 替换七人顺序式占用惩罚，加入容量、排队和估算用时仿真。
5. 加入 USB 摄像头、基准帧、变化检测、防抖和实时改路。
6. 加入历史场景、不可变版本、本地排行榜和导入导出。
7. 接入可选账号、CloudBase 同步、团队角色、私有图片和服务端校验排行。
8. 完成移动端、性能、安全、识别误差和断流验收后发布。

云端阶段交付数据库迁移脚本、安全策略和配置说明，不把任何真实密钥提交到 GitHub。CloudBase 项目尚未配置时，发布版本保持完整的游客本地模式并明确显示“云同步未启用”。

“代码实现完成”和“公开实例云端激活”分开验收：前者要求同步适配器、数据库迁移、权限策略、云函数与自动化集成测试齐全；后者只有在项目所有者提供有效 CloudBase 环境并完成微信/短信等外部资质配置后，才能通过真实账号、跨设备、分享撤销和服务端排行的端到端验证。

识别准确率发布还依赖用户采集或提供满足第 16.1 节分层要求的至少 30 张标注照片，并需要技拓摄像头实机参与设备与延迟验收。当前已有照片可用于开发和回归示例，但不足以声称达到跨布局、跨设备的正式识别指标；在数据集与实机门禁完成前，公开页面必须保留“候选结果需人工复核”提示。

## 18. V1.0 迁移

- 当前演示沙盘迁移为内置只读示例场景，并保留正确的 E1/E2、安全泡沫边界和 5 格最低净宽规则。
- 现有 A* 可作为时间层的底层搜索工具，但不再直接用风险、拥堵和距离加权总和决定最终路线。
- 现有绿色区域检测迁移为 `PerceptionAdapter` 的一个检测器，不再直接清空用户已确认的起点。
- 现有矩形标注继续支持，同时新增画笔、多边形、移动和分层复核。
- 旧页面 URL 保持可访问；本地存储使用独立的 `schemaVersion: 1.1`，不猜测迁移不存在的旧历史数据。

## 19. 完成定义

V1.1 只有在以下条件全部满足时才算完成：

- 照片/拍照入口可在受支持手机浏览器使用；USB 实时入口可在桌面 Chrome/Edge 与被操作系统实际暴露为视频输入的兼容移动设备使用；
- 新图上传后自动产生完整候选场景，人工可逐类修正；
- 实时模式能够发现火源和障碍变化、计算道路剩余净宽并自动改路；
- 路线选择严格满足“安全 > 堵塞 > 速度”；
- 七人联合仿真可输出个人与全员模拟用时；
- 未登录用户可以保存和查看本地历史；
- 已配置云端时能够完成跨设备同步、团队角色和服务端校验排行榜；
- 识别不确定、摄像头断流或没有安全路线时，不会展示误导性的安全结论；
- 全部自动化测试、移动端检查和公开部署验证通过。
